DNS Transparent Proxy Detection Script – README

Overview

What This Script Is

This is a PowerShell-based DNS testing harness that:

  • Runs dig commands (either locally or via SSH to a remote host).
  • Parses the output to check for specific DNS behaviors.
  • Supports 7 different DNS tests on a selected root nameserver plus an option to run all of them.
  • Supports 3 other tests that can detect transparent DNS proxy servers.

 

This PowerShell script runs a series of DNS tests to detect the presence of transparent DNS proxies, DNS manipulation, or unusual resolver behavior.
It can run dig locally (if dig.exe is available) or remotely via SSH to a Linux/Unix host with dig installed.  You must have an account on the remote host.

That feature is most useful if the remote host is on a network that has been verified to not be behind a transparent DNS proxy.

The script supports 8 individual tests and an "All Tests" mode.

Requirements

Windows

  • PowerShell 5.1 or later (included in Windows 10/11)
  • dig.exe for Windows (optional if running locally)
    • Download from:
      • ISC BIND 9.16.50 Downloads (This is the last Windows version, build in 2024, even though it’s a prior version, it does not support DoH)
      • Or from ISC BIND 9.17.15 (this version was built in 2021, but it supports DoH)
    • Extract the zipfile and copy dig.exe and all the DLLs into the same folder as this script.
    • Run dig at the CMD command line and make sure you get output

Remote SSH Option

  • A Linux/Unix host with:
    • dig installed (sudo apt install dnsutils on Debian/Ubuntu, sudo yum install bind-utils on CentOS/RHEL)
    • SSH access enabled
  • Windows must have ssh.exe available (included in Windows 10/11).

Installation

  1. Download the script and save it as:

dns-proxy-test.ps1

  1. Optional: Download dig.exe for Windows and place it in the same folder as the script.
  2. Open PowerShell and navigate to the script folder:

Powershell

cd "C:\path\to\script"

  1. Allow script execution (if not already enabled):

Powershell

Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass

Usage

Run the script:

Powershell

.\dns-proxy-test.ps1

You will be prompted to:

  1. Choose local or remote mode:
    • If dig.exe is found locally, you can choose to run locally or via SSH.
    • If not found, you must enter a remote SSH host (e.g., user@hostname).  The best results will come from selecting a remote host that is on a different network than the one you are testing from.
  2. Select a root DNS server from the provided list.
  3. Select a test (1–12) or Run Tests 1-8 (option 13).

Tests detailed descriptions

Test 1 – NSID Check

  • Sends an EDNS(0) NSID request to the selected root server.
  • PASS: NSID is returned (server identity visible).
  • FAIL: No NSID returned (proxy may be stripping EDNS options).

Test 2 – RA Bit Check

  • Queries selected root server with recursion disabled.
  • PASS: RA (Recursion Available) bit is not set.
  • FAIL: RA bit is set (proxy may be answering recursively).

Test 3 – Custom EDNS Option Echo

  • Sends a custom EDNS option (code 65001) with test data to selected nameserver.
  • PASS: Option is echoed back.
  • FAIL: Option missing (proxy may be altering packets).

Test 4 – Large DNSSEC UDP Response / TC Bit

  • Requests DNSSEC DNSKEY from selected nameserver with small buffer size (+bufsize=512) and +ignore.
  • PASS: TC (Truncated) bit is set (expected for large UDP responses).
  • FAIL: TC bit not set (proxy may be altering packet size or forcing TCP – however some transparent proxies will pass this test).

Test 5 – Malformed/Unusual Query

  • Sends a mixed-case label with uncommon QTYPE (TYPE65) to selected nameserver.
  • PASS: NXDOMAIN returned.
  • FAIL: Unexpected response (proxy may be rewriting queries).

Test 6 – Long Label + Private QTYPE

  • Sends a long label with private-use QTYPE (65534) to selected nameserver.
  • PASS: NXDOMAIN returned.
  • FAIL: Unexpected response.

Test 7 – Glue TTL Consistency

  • Checks TTL values of glue A/AAAA records in Additional section from selected nameserver.
  • PASS: All TTLs match.
  • FAIL: TTLs inconsistent (proxy or resolver may be altering glue records).

Test 8 – Nonexistent DNS Server Query Test

  • Checks to see if a query to a nonexistent DNS server fails.
  • PASS: Query to nonexistent DNS server fails.
  • FAIL: Query to nonexistent DNS server succeeds (proxy is ignoring target DNS server and responding anyway).

DNS Proxy / Interception Detection Tests

Test 9 – DoH + NSID

Purpose:


Verifies that Google’s public DNS server queried over DNS‑over‑HTTPS (DoH) returns a valid Name Server Identifier (NSID) via EDNS(0).
This confirms that the query reached the intended authoritative or recursive server without being intercepted or altered.  Since a transparent DNS proxy cannot decrypt a DoH packet it’s only 2 choices are to either block it completely in which case the query will fail, or to ignore it and allow it to pass.  The root nameservers are not used for this test because they do not support DoH.  A NSID is used as further proof a transparent proxy is not intercepting the query.

 

How it works:

  1. Sends a DNS query for a known domain (e.g., example.com) using DoH to a specified resolver (e.g., @8.8.8.8).
  2. Includes the EDNS(0) NSID option in the query.
  3. The server, if compliant, returns an NSID value in the OPT pseudo‑section of the DNS response.
  4. The parser checks for the presence of the NSID field:
    • PASS → NSID present.
    • FAIL → NSID missing (possible interception or non‑support).

Interpretation:


A PASS here means the DoH path is working and the resolver supports NSID.

 

Test 10 – UDP + NSID

Purpose:


Verifies that the same DNS server queried over standard UDP port 53 also returns a valid NSID.
This checks whether the unencrypted DNS path is being intercepted, altered, or blocked.

 

How it works:

  1. Sends the same DNS query for the same domain using UDP to the same resolver.
  2. Includes the EDNS(0) NSID option in the query.
  3. The server should return the same (or at least a valid) NSID in the response.
  4. The parser checks for the NSID field:
    • PASS → NSID present.
    • FAIL → NSID missing (possible interception, stripping, or non‑support).

Interpretation:

A PASS here means the UDP path is working and the resolver supports NSID.
A FAIL here, when Test 9 passes, may indicate interception or modification of UDP DNS traffic.

Test 11 – Interception Detection Meta‑Test

Purpose:
Compares the results of Test 9 (DoH) and Test 10 (UDP) to detect possible DNS interception or manipulation.

 

How it works:

  1. Runs Test 9 and records its PASS/FAIL result.
  2. Runs Test 10 and records its PASS/FAIL result.
  3. Displays a summary table showing both results (color‑coded in console output).
  4. Applies comparison logic:
    • PASS (No interception detected) → Both Test 9 and Test 10 pass.
    • FAIL (Likely interception) → Test 9 passes but Test 10 fails.
    • FAIL (DNS resolution broken or blocked) → Both fail.
    • FAIL (Inconsistent results) → Any other combination.

Interpretation:

  • PASS: No interception detected → Both encrypted and unencrypted DNS paths return NSID.
  • FAIL: Likely interception → Encrypted DoH works, but UDP DNS is altered or blocked.
  • FAIL: DNS resolution broken or blocked → Neither path works.
  • FAIL: Inconsistent results → Unexpected mismatch; requires manual review.

 

Technical Notes:

  • NSID (Name Server Identifier) is defined in [RFC 5001] and is an EDNS(0) option that allows a server to identify itself in responses.
  • These tests rely on the dig command’s +nsid option to request the NSID.
  • Test 11 does not send its own DNS queries; it calls Tests 9 and 10 internally using the same execution logic (local or SSH) to ensure consistent conditions.

Test 12 – DNS Root Server Query Speed Measurement

Purpose:

Test 9 measures the response time (in milliseconds) from each of the 13 DNS root servers when queried directly.

If a transparent DNS proxy is present the response times for all servers will be almost identical particularly if the test is run multiple times.  If a transparent proxy is NOT

present then the response times will have differences of at least 50ms or more because the root nameservers are scattered across the globe, the furthest ones will be greater than 100ms response time.

How It Works

1.   Root Server List
The test uses a predefined list of the 13 official DNS root servers (A–M), each with its IPv4 address.

2.   Query Method
For each root server:

    • A dig command is executed with the following options:
      • +norecurse – Requests a non-recursive query so the root server responds directly without forwarding.
      • +time=5 – Sets a 5‑second timeout for the query.
      • +tries=1 – Ensures only one attempt is made per server.
      • example.com A – Requests the IPv4 address (A record) for example.com.
    • The query is sent directly to the root server’s IP address using the @<IP> syntax.

3.   Output Capture
The script captures the entire output from dig to ensure the Query time: line is included.

4.   Response Time Extraction
The script searches the output for the line:

;; Query time: <number> msec

and extracts the numeric value.
If no such line is found, the result is recorded as TIMEOUT.

5.   Result Table
The results are stored in a table showing:

    • Server – Root server name (A–M).
    • IP – IPv4 address of the root server.
    • TimeMs – Response time in milliseconds, or TIMEOUT if no response was received.

6.   Sorting
The table is sorted so that servers with numeric response times appear first, and TIMEOUT entries appear last.

Example Output

Server IP             TimeMs

------ --             ------

K-root 193.0.14.129   18

B-root 170.247.170.2  22

A-root 198.41.0.4     25

...

J-root 192.58.128.30  TIMEOUT

Notes

  • This test uses direct queries to root servers and does not rely on the system’s configured DNS resolver.
  • A TIMEOUT does not necessarily mean the server is unreachable — it may be due to packet loss, temporary congestion, or filtering.
  • The test uses UDP by default.
  • The short delay between queries prevents socket reuse issues on Windows.

Tips

  • If running remotely, ensure your SSH key or password authentication works before starting.
  • If you see "No output from dig", check firewall rules and that the root server IP is reachable.
  • You can add more root servers to the $rootServers array in the script.
